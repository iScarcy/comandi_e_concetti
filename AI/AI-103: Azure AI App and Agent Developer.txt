SECTION 1
    UNIT 1 - WHAT IS AN AI AGENT ?
    *** An AI agent is a software service that works independently to complete tasks for users

    THE TREE CAPABILITIES OF EVERY AGENT 

    REASONING - Making Decisions: AIUTA L'AGENTE A PRENDERE DECISIONI ARRIVANDO ALL'OBIETTIVO STEP BY STEP
    TOOL USE - TAKING ACTION: L'agente può chiamare servizi esterni per avere risorse a disposizione
    MEMORY - REMEMBERING CONTEXT: l'agente ha disposizione le conversazioni precedenti per simulare una memoria umane e prendere decisioni in un consteso più ristrestto

    SYSTEM MESSAGE IS A SETS RULES AND TONE TO HOW THE AGENT SHOULD ACT AND ANSWER USER REQUESTS. 

    SIMPLE API Call vs. AGENT 
    Una semplice invocazione di API prevede una domanda e una risposta, non c'è memoria. 
    Il workflow di un agente è più complesso, se per esempio riceve la domanda "che tempo fa?" l'agente può decidere di chiamare un servizio meteo trami API tool e formulare una risposta per l'utente in base alle impostazioni del contesto. L'agente può ricordare la città dell'utente per le prossime chiamate.

    STATEFUL VS. STATELESS: Le semplici chiamate api non hanno memoria, un agente invece simula di avere memoria perché riusa la cronologia delle conversazioni in chat e utilizza le informazioni del contesto

    LLM (Large Language Model) è un modello statistico allenato da bilioni di esempi di testi per prevedere la prossima parola in una seguenza.
    Gli LLM hanno un ruolo negli agenti perché ne sono il cervello, loro leggono ad interpretano le richieste dell'utente e decidono la prossima da fare
    ma da soli non possono fare nulla: non possono chiamare API, fare ricerche nel web. Sarà l'agente, in base all'output prodotto dal LLM, a chiamare un servizio esterno o lanciare un programma.

    TOOL CALLING: E' l'abilità di un agnte di richiedere e eseguire funzionalità esterne come una ricerca su un database o l'invio di una meali
        -> come funziona ? l'LLM genera un output strutturato dicendo "ho bisogno di chiamare il servizio X con i parametri Y" e l'agente esegue.
        --> senza il TOOL CALLING un LLM potrebbe solo parlare ma con esso può triggerare una reale azione nella realtà

    MEMORY: la memoria per un agente significa il memorizzare le informazioni fornite dalla passate interazioni per usarle in futuro
        -> Short - Term Memory (Session Context): Memoria a breve termine, un agente ricorda le informazioni date dall'utente nella stessa chat 
        -> Long - Term Memory: La memoria a lungo termine che viene usata attraverso le sessione di conersazioni dell'utente
        --> senza la memoria noi dovremo reinviare l'intera cronologia della conversazione ad ogni richiesta. Con la memoria, gli agenti salvano e usano le informazioni del contesto in modo più efficente.

    WHAT IS MICROSOFT FOUNDRY ? 
    E' una piattaforma cloud MICROSOFT dove si può creare, deployare e gestie agenti AI 
        -> E' una "One stop shop": Foundry provvede a ciò che abbiamo bisogno, deployare un modello, gestire le autorizzazioni, usare tool sicuri. Il tutto in singolo servizio Azure
        -> Foundry è il successore di AZURE AI STUDIO
        -> Foundry include Hubs (container), Projects (agent workspace) e Agent Service (ambiene di deploy e esecuzione agenti)

    Foundry TRACE: è un tool di debugging che mostra ogni decisione e azioni dell'agente durante una conversazione 
        -> Definizione: Un trace è come fosse un log registrato ad ogni passo compiuto da un agente (con timestamp e risultato)
        -> Quando avviene un reasoning loops, ovvero un loop in un cui un agente repere la stessa decisione più volte senza andare avanti, 
        Foundry Trace mostra esattamente il loop da dove è partito e dove avvengono eventuali eccezioni che generato il loop durante la conversazione.

    Entra Agent ID: E' una features di sicurezza che da ad ogni agente una propria indentità separata da un utente umano
        -> Prima gli agenti scrivevano codice come un utente, adesso un Entra Agent ID da ad ogni agente una propria identi con dei permessi
        SPONSORE CONCEPT: Uno sponsor è un umano che è responsabile delle azioni di un agente. Nonostante l'agente abbia il proprio ID, lo sponsor umano è responsabile del comportamente dell'agente.

    Content Safety: è un servizio azure che analizza l'input e l'output di un agente per verificare se ci sono contenuto dannosi come parole violente    

    Red Teaming for agents
        -> Definizione: il red team agent è un team che intenzionalmente prova a complire il tuo agente attraverso l'invio di JAILBREAK ATTEMPTS, prompt injections and input inaspettati
        --> Un Jailbreak è un prompt attentamente progettato con lo scopo di agirare il sistema dei messaggi dell'agente e i filtri di sicurezza, cosi il nostro agente ignoreranno le propri istruzioni
        -- Prompt Injection Explained: La prompt injections si ha quando nell'input dell'utente sono inclusi comandi nascosti che sovrascivono le originali istruzioni dell'agente.

    UNIT 2
    MICROSOFT FOUNDRY è un singolo servizio di Azure che provvede al deploy dei modelli, hosting per agenti, sicureza e tool di debug.

    FOUNDRY HUBS: è un container di altro vicello che racchiude tutti i progetti agentici, modelli e impostazioni di sucurezza.
        Definizione: Un HUB è come una cartella che contiene qualsiasi cosa relaziona al tuoi teams di lavoro AI 
        -> Hub vs Azure Subscription: Una sottoscrizione Azure può avere moltipli Hub e ogni Hub può avere le proprie regole d'accesso, cost di tracciamento e collocazione regionale
        --> Quando crere un Hub ? un hub va creato per business unit. Hub isola agents, modelli e costi da altri gruppi nella stessa azienda

    FOUNDRY Projects: E' un workspace interno di un HUB dove si possono creare, restare e deployare agenti specifici o gruppi di agenti relazionati
        Definizione: Un progetto (Projects) contiene qualsiasic cosa per un "agent soluction": il codice dell'agente, system message, definizione  di tool, configurazione della memoria e trace log.
        -> Projet vs. Hub Relationshio: Un HUB può contenre diversi progetti e ogni progetto eredita le impostazioni di sicurezza dal suo HUB ma può avere anche la propria specifica configurazione.
        --> Un Projet potrebbe contenere un customer support agent. Un altro progetto nello stesso Hub potrebbe contenere un separato catologo gi gestione degli agenti.

    FOUNDRY Agent Service: è un ambiente di runtime dove deployare agenti, eseguirli e rispondere alle richieste utenti
        Definizione: Un Agent Service è una piattaforma di hosting completamente dedicata alla gestione. Si può uploadare il codice degli agenti, eseguirci servizi, scalarli e monitorarne la vita.

    FOUNDRY Model Catalog: è una lista di modelli AI pre allenati che si possono deployare e usare come cervelli dei nostri agenti 
        Definizione: The model Catalog mostra tutti i modelli disponiile da MICROSOFT (Phi series), OpenAI (GPT-5) e altri provider.    
 
     WHAT IS AN EndPoint ? 
        Definizione: Quando si deploya un modello o un agente, Foundry da un URL con il quale raggiungere il nostro codice applicativo.
        -> Senza un URL, la nostra applicazione non avrebbe una modo come raggiungere il modello deployaiato o l'agente.
        --> Ogni EndPoint ha associato un API Key che provvede ad autorizzare le chiamate verso l'end point 

    API KEYS: è una stringa segreta di caratteri che identifica la nostra applicazione e provvede a darle i permessi necessari per invocare un EndPoint.
        Definizione: Un API KEY è come una password per il nostro codice, deve essere incluso in ogni richiesta verso l'EndPoint
        --> Una buona best practice sarebbe quella di cambiare l'API KEY regolarmente.

     --------> RIASSUNTO FOUNDRY Projects GERARCHIA <-----------

    LIVELLO 1: Azure Subscription, il Top Container. Una Subscription contiene multiplu HUBS
    LIVELLO 2: FOUNDRY Hub, contiene Projects, modelli condivisi e policies di sicurezza condivise 
    LIVELLO 3: FOUNDRY Projects: Contiene codice degli agenti, tool definitions, impostazione di memoria e trace logs.
    LIVELLO 4: Agent Service Deployment: L'istanza in esecuzione del proprio agente. Gli agenti sono deployati da un Projet e ognuno ha il proprio URL and API KEYS.

    Agent Identity Bluprints: è un template che definisce permessi e regole di accessi che un agente dovrebbe avere quando è deployaiato.
        Definizione: Un Blueprint è un file di  configurazione riusaibile che specifica quale database, APIs, e storage un agente può avere accesso.
        - > Quando usare un Blueprint ? Invece di configurare i permessi di ogni singolo agente, possiamo creare un Blueprint e usarlo per tutti.
        Blueprint vs. Agent ID: sono due concetti diversi, l'Agent ID è un'identità unica mentre Blueprint è un template di permesse applicati ad un'identità.

    Conditional Access for Agents: è una feature di sicurezza che verifica delle condizioni, come localiccazione per esempio, prima di permette ad un agente di agire.
        -> Per esempio possiamo richiedere ad un agente di essere eseguito dalle 9 AM e le 5 PM, prima di esegure l'agente verifica l'orario.

    Access Packages for Agents: pacchhetti di permessi che si possono assegnare all'identità degli agenti, hanno una data di scadenza.

    **** SPONSOR LIFECYCLE ****
        Abbiamo detto che uno sponsor è un umano che è responsabile delle azioni di un agente e deve approvare certi comportamenti.
        -> Definizione: Ogni agente con un Entra Agent ID deve avere uno sponsor. Questa persona è responsabile se l'agente non ha un buon comportamento o viola le policies 
        --> Responsibilità: Lo sponsor riceve i log dell'agente, approva le richieste di Access Packages e viene contattato se l'agente fa scattare un security alert.
        ---> Lifecycle Management: Quando uno sponsor lascia l'azienda, l'agente assegnato viene sospeso fino a quando un nuovo.

    *** CODING PATTERN ***
    I nostri agenti devono recuperare EndPoint URL e API KEYS dalle configurazioni e queste non devono MAI ESSERE SCHIANTANTE NEL CODICE A MANINA.
    --> Enviroment Variables Pattern: Salvare/Usare 'FOUNDRY_ENDPOINT' e 'FOUNDRY_API_KEY' come variabili d'ambiente. Il nostro codice le dovrà leggere come os.getent('FOUNDRY_ENDPOINT')
    --> Azure Key Vault Pattern: Per produzione, salviamo le chiavi segrete in Key Vault. I nostri codici di autenticazione sono salvati prima in Key Vault e dopo recuperati per gli EndPoint e le chiavi di sicurezza.
    --> DefaultAzureCredential Pattern: Usare 'DefaultAzureCredential()' nel codice, questo prova automaticamente multipli metodi di autenticazione come variabili d'ambiente, gestione dell'identità, Visual Studio pop up, etc.
